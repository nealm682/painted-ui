The Split Brain

Painted UI and on-device inference — what the cloud composes, what the phone reacts to, what needs no model at all, and what it costs you. Companion to The Cast and The Choreographer.
The short answer: yes, Painted UI benefits from on-device inference — and it benefits more than most generative-UI approaches do, for a structural reason: the hard part was already moved off the model. A phone-sized model doesn't have to be a good designer here. It only has to name what changed. Local code owns everything else.

The catch: a small model on a phone can no longer emit a broken patch — the operating system guarantees the format — so instead it occasionally emits a wrong one, silently, and it renders perfectly. You trade loud failures for quiet ones. That trade is worth making, but only if you add a cheap checker. Scroll to The Catch for the honest version.

What you gain

  • Per-user model cost → $0. The Director is the only role that ever cost money. On device, that line disappears.
  • Taps answer without a round trip. No network, no queue, no cold start — motion begins in the same beat as the touch.
  • Painting ahead becomes free. Speculative pre-paint is wasteful when tokens cost money; on device it costs battery and nothing else.
  • Works on a plane. Offline, private, nothing leaves the device.
  • The parser layer disappears. Patches arrive as typed objects in-process, not text over a wire.

What you don't

  • A better painter. The phone model is smaller and weaker. Cheaper and faster — not smarter.
  • Judgment under constraint. Forcing a schema onto a ~3B model measurably degrades its choices even as it guarantees the format.
  • Loud failures. They go silent. A wrong patch now renders instead of crashing.
  • A short output budget. Phone memory bandwidth is 30–50× narrower than a datacenter GPU's. Output tokens stay scarce — permanently.
  • One codebase. Two brains means two prompts, two grammars, and a handoff to keep honest.

1 · Two brains, one stage

Painted UI has always had exactly one expensive role. In The Cast: the Director decides what exists and what changes; the Choreographer turns each change into motion; the Animator draws at 60fps; the Stage holds the nodes. Only the Director costs money, because only the Director is a model.

On-device inference doesn't replace the Director. It splits it — into a slow, expensive, thoughtful one in the cloud and a fast, free, limited one in your pocket, both writing to the same stage in the same patch language.

The row that surprises people is the third block. In a painted interface, most of what moves needs no inference at all. That's why a weak local model is enough — it isn't being asked to do the expressive work.

3 · What a streamed patch actually looks like

Same intent, three forms — on the wire from the cloud, in memory on the device, and after the Choreographer has had its say. Open them in order.

A · From the cloud — text, arriving token by token

One JSON object per line, streamed. The parser scans brace depth and emits a patch the instant an object closes — which is why the screen assembles while the model is still talking.

{"op":"palette","set":{"bg0":"#101a2a","accent":"#e8a34c"}}
{"op":"add","node":{"id":"title","kind":"text","x":0.5,"y":0.14,
        "text":"Harbor — Tuesday","z":3}}
{"op":"add","node":{"id":"c2","kind":"card","x":0.5,"y":0.56,
        "w":0.2,"h":0.3,"label":"Berth 7","z":2}}          // ~40 tokens
{"op":"done"}

Cost shape: ~700 ms before the first token appears (network + queue + prefill), then tokens arrive in a burst. You pay per token, per user, every time.

B · On the device — the same patch, as a typed object that cannot be malformed

There is no wire and no text. The OS runs constrained decoding against a schema you declare, so the model's output is a typed object — the shape is enforced during generation, not validated after.

// Swift — Apple Foundation Models
@Generable struct Patch {
  @Guide(description: "what changed — never how it moves")
  var op: Op                      // enum: add | update | remove | scene | focus
  var id: String
  var set: Props?                 // x, y, w, h as 0…1 fractions
  var intent: Intent?             // action / importance / cause
}
// Kotlin — ML Kit GenAI / Gemini Nano, same idea
data class Patch(val op: Op, val id: String,
                 val set: Props? = null, val intent: Intent? = null)
The failure classes that broke exp-03 twice — the model narrating instead of painting, and .5 written where 0.5 was required — become unemittable. Not "caught". Not "retried". They cannot be produced.

Cost shape: ~0 ms to first token (nothing to wait for), then slow steady decode. You pay nothing, ever. The scarce resource flips from money to output tokens.

Field names are not free. The words in that schema — op, intent, importance — are read by the model on every emission; they instruct it as much as the prompt does. Minifying emphasize to e saves tokens and costs quality. Compress the values, keep the keys meaningful.

C · What the Choreographer turns it into — the part no model touches

The Director said what. It said nothing about motion. Local code decides all of that, in microseconds, identically on both brains:

choreograph({op:"update", id:"c2", set:{w:0.34}}, node, mood)
  → { tween:true, dur:1100, ease:"inout", kind:"morph" }
     // same id + new numbers ⇒ the same thing changing ⇒ morph, never blink

choreograph({op:"scene", focus:["c2"], mode:"spotlight"}, …)
  → siblings: { tween: alpha → 0.35, dur:600 }        // recede
     focus:   { tween: scale → 1.06, dur:600 }        // advance
     // the model named an INTENT; the choreographer produced six animations

D · The check that runs after — the verifier

Deterministic, no inference, ~100 lines. It exists because the format guarantee removed the parser's accidental safety net (see The Catch).

verify(patch, stage) {
  // geometry
  reject if node.x < 0 || node.x > 1 || node.y < 0 || node.y > 1   // off-screen
  reject if textWidth(node) > container(node).w                    // overflow
  reject if contrast(node.fill, behind(node)) < 3.0                 // unreadable
  // references
  reject if patch.id ∉ stage.nodes                                  // dangling target
  reject if patch.op === "scene" && result.visibleNodes === 0        // empties the screen
  // coherence
  flag   if node.hasActiveTween && patch.contradicts(node.tween)     // interruption case
}

A rejected patch has two honest destinations: quarantine (repaint from last-good and move on), or hand it back to the Director as a message — which fits the architecture already, since clicks are messages too. A failed check is just another event the Director hears.

Where does it live? Probably inside the Choreographer, not beside it — the Choreographer is the only component that already knows every node's position, what's mid-animation, and what the layout resolved to. That's exactly the knowledge a verifier needs.

5 · The catch — what you're actually trading

Here is the finding that changed this page. Forcing a small model to fill in a schema is like making someone solve a hard problem while speaking a language they're half fluent in. They stop making grammar mistakes — and start saying more wrong things, because the effort went into the grammar.

6 · The honest cost list

Costs you'll actually feel

  • Silent wrongness. Covered above. Non-negotiable: build the verifier first.
  • Two Directors to maintain. Two prompts, two grammars, and a handoff policy that can drift.
  • A hard output budget. Phone memory bandwidth (50–90 GB/s vs a datacenter GPU's 2–3 TB/s) makes decoding slow in a way faster chips won't fix. A verbose protocol will never fit.
  • Battery and thermals. Cheaper than a datacenter, not free. Pre-painting ahead is "free" in dollars and not in milliamp-hours.
  • Platform lock. Guided generation is an OS feature. iOS and Android give you different guarantees; the browser gives you fewer still.
  • A weaker first scene. If the device composes from cold, it's noticeably less good than the cloud would have been.

Why Painted UI absorbs them well

  • Tiny output by construction. Patches, not component trees, not pixels. The scarce resource on a phone is exactly the one we use least.
  • The model doesn't need taste. It names the change; the Choreographer owns expression. A weak model is sufficient here in a way it isn't elsewhere.
  • Wrong is visible. In a chatbot a wrong-but-valid answer just looks like an answer. On a canvas it's off-centre, overlapping, or unreadable — checkable with geometry.
  • The handoff already exists. Clicks are messages; patches are patches. Two Directors writing to one stage needs no new protocol.
  • Graceful degradation. Lose the device model and you're back to today's architecture. Lose the network and you keep reacting.
Where this leaves the concept. On-device inference is a poor fit for generative UI in general — it asks a small model to author a whole interface — and an unusually good fit for Painted UI, because the expensive judgment was moved into deterministic local code years before the hardware made that mandatory. The Choreographer was built as a cost optimization. On device it turns out to be the reliability layer. That's the finding worth keeping.
