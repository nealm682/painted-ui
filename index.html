The architecture

Four roles. One shared stage.

The architecture works because intelligence, motion policy, state, and rendering are separated. Each operates at its own speed without blocking the others.

01 · LLM / agent

Director

Decides what exists and what changes. Emits semantic operations instead of pixels or animation timelines.

02 · motion policy

Choreographer

Decides how changes move: verb, duration, easing, direction, and stagger. A pure function of each patch — not a separate agent. In production it becomes a versioned motion design system.

03 · node map

Stage

Holds persistent semantic objects. Stable IDs preserve identity, enabling morphing, continuity, and interruption handling.

04 · frame-rate loop

Animator

Samples tween state at display rate and applies it to the render target — canvas in today's demos, component trees (DOM / A2UI-style) via adapters. Executes approved motion verbs and never waits for the network.

Motion physics · experiment 14

Interrupt the choreographer.

An agent changes its mind mid-animation. That is the normal case, not the edge case — and it is where duration-and-easing quietly falls apart. One patch stream, three motion engines, same scene, same targets, same frame loop.

A ease-in-out B ease-out C spring retarget instant velocity of the hero card, sampled every frame
Both tweens drop to zero at every retarget line. A duration tween is a scripted path from A to B, so a new instruction restarts the script from rest. The spring passes through continuously — its velocity is state, not a function of scripted position. The jump is exactly zero, not merely small: v₀ is assigned from the evaluated velocity, so continuity is structural rather than tuned.

There is no easing that avoids both failures.

The first version of this rig compared springs against a single cubic ease-in-out — the one easing that fails hardest — which was stacking the deck. Adding an ease-out arm produced a better finding than the original claim. Ease-in-out spends its opening barely moving: 180 ms into a 500 ms tween it has delivered 18.7% of the commanded distance, so under rapid fire it restarts the slow-in ramp forever and stalls. Ease-out delivers 73.8% in the same window and keeps up — but it is moving fastest at the exact moment it gets dead-stopped, so its snap is roughly twice as violent.

Headless simulation using the same sampler this page runs · playful scheme, ζ 0.50 · 180 ms retarget interval · normalised to a 700 px pane. Front-load the curve and you travel well but snap hard; back-load it and you snap softly but stall. The spring does neither — not by tuning, but because velocity is state.

All three engines finish at 0 px final error. The tweens are not going to the wrong place — they are going there late. The failure is temporal, which is why it survives screenshot review and dies on contact with a hand.

The same physics on real components.

Not just cards sliding around. Press and hold each button. The two spring buttons compress immediately — a spring front-loads its velocity, so the response lands inside the first frames. The tween button spends its ease-in ramp before anything visible happens, which is why it reads as though it didn't register the press.

press a button…
What this changes — and what it doesn't. The protocol is untouched: the Director still emits {"op":"update","id":"cost"} and says nothing about motion. Only the Choreographer's output type changes — from a duration and an easing curve to a damping ratio and a stiffness. Same governance boundary, same token cost, one fewer failure mode. And it compounds with the section below: springs front-load velocity, so the first 100 ms after a tap carries almost all of the motion — which is exactly the window an on-device Director is trying to win.
Status — measured, not yet validated. The velocity discontinuity is instrumented and reproducible. Whether a naive viewer reads the tween's dead stop as broken or merely different is an open question awaiting a field run, and it is not claimed here. Nor is it settled whether the stall reads worse than the snap — if it doesn't, ease-out is the wrong tween default even though it travels better, which would invert common practice.
On-device inference

The split brain.

The Director is the only role that ever cost money. Split it — a slow, thoughtful one in the cloud, a fast, free, limited one in your pocket — and both write to the same stage in the same patch language.

The short answer: Painted UI benefits from on-device inference more than most generative-UI approaches do, for a structural reason: the hard part was already moved off the model. A phone-sized model doesn't have to be a good designer here. It only has to name what changed. Local code owns everything else.

The catch: a small model on a phone can no longer emit a broken patch — the operating system guarantees the format — so instead it occasionally emits a wrong one, silently, and it renders perfectly. You trade loud failures for quiet ones. Worth making, but only with a cheap checker. Jump to the catch ↓

cloud director

Composes

  • First rich scene. Needs taste, world knowledge, and hundreds of output tokens at once. A phone would take 15–30 s.
  • Reasoning over real data. “Why did delays increase?” is a thinking problem, not a painting problem.
device director

Reacts

  • Click → mutation. One or two patches. A round trip would cost more than the decision.
  • Emphasis, mood, small edits. Cheap, frequent, and the user is watching. Latency is the whole product here.
  • Speculative pre-painting. Free tokens against an already-warm scene.
no model at all

Moves

  • Entry/exit motion, easing, stagger. The Choreographer. Deterministic code — never a model's job.
  • Layout re-solve on rotate/resize. Constraint solver plus springs. Zero inference.
  • Checking a patch makes sense. Geometry checks, ~100 lines.

The catch — what you're actually trading.

Forcing a small model to fill in a schema is like making someone solve a hard problem while speaking a language they're half fluent in. They stop making grammar mistakes — and start saying more wrong things, because the effort went into the grammar. Measured across 15,000 generations on sub-3B models, free-form output versus hard schema-constrained decoding:

Both of exp-03's live failures were loud. Their on-device replacements are quiet. That is a strictly harder debugging problem, and it is the single most important thing to understand before shipping a phone-side Director. The mitigation is not a smarter model — it's a ~100-line deterministic verifier inside the Choreographer, which already knows every node's position, what's mid-animation, and what the layout resolved to.

Where this leaves it. On-device inference is a poor fit for generative UI in general — it asks a small model to author a whole interface — and an unusually good fit for Painted UI, because the expensive judgment was moved into deterministic local code before the hardware made that mandatory. The Choreographer was built as a cost optimization. On device it turns out to be the reliability layer.

Enterprise value

Generative UI with a governance boundary.

The model controls meaning and intent. The product team controls visual language, motion, accessibility policy, and rendering code.

Model micromanages the UI

High expressiveness, but every detail becomes a probabilistic output.

  • More tokens and latency
  • Inconsistent brand behavior
  • Difficult to unit test
  • Unsafe to allow arbitrary code
  • Transitions may conflict or snap

Model directs a governed runtime

Meaning stays generative while execution remains deterministic.

  • Small allow-listed protocol
  • Versioned motion design system
  • Replayable and auditable patches
  • Client-side performance
  • Optional model overrides within policy
The honest claim

A distinctive synthesis—not magic.

“Traditional design systems govern what components look like. Painted UI adds a governed vocabulary for how generated experiences come into existence and change over time.”The contribution is the composition: semantic streaming, persistent identity, local choreography, and continuous rendering.
Established ingredients: scene graphs, tweening, streaming protocols, game loops, and immediate-mode rendering.
Distinctive synthesis: using those ingredients as a semantic motion runtime for model-authored interfaces.
Not yet proven: broad enterprise task coverage, accessibility, measurable usability gains, and superiority to component UI.
Measured, not yet validated: the interruption result above is instrumented and reproducible; whether a naive viewer reads the tween's dead stop as broken rather than merely different awaits a field run.
Likely production form: a hybrid—standard accessible components plus Painted UI for focus, continuity, explanation, and transitions.
